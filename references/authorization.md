# 一键授权接入设计

## 已有能力与待完成部分

默认 Key 的创建、获取和复用已有实现。新用户注册时发放默认 Key，已有用户复用其默认 Key，并保留用户设定的权限。

浏览器授权页面、授权回传协议以及 Skill 自动保存的完整链路尚待完成。当前没有已验证可用的公开授权 URL。README 和技能提示应将一键授权明确标为待接入，不把页面登录成功等同于密钥已经传回。

## 目标体验

1. Skill 检查本地是否已有用户 Key，有则复用。
2. 未配置时，打开平台正式提供的授权页，用户登录并确认授权。
3. 平台在用户登录会话内创建或获取其默认 Key。
4. 通过正式回传协议将授权结果交给本地客户端。
5. 客户端验证结果后，调用 `scripts/humanize.py` 的 `save_key()` 存入本地私有配置，后续仍通过已发布的去 AI 接口调用。

设计不要求用户手动新建 Key、勾选权限、复制密钥作为唯一默认流程。`configure` 和 `QILING_API_KEY` 是现在可用的兼容方式，不要求用户在聊天中提交密钥。

## 平台已经具备的内部获取接口

登录后的平台页面使用 `POST /api/v1/customer/open-api/keys/default/reveal`；同站前端通过 `/api/customer/open-api/keys/default/reveal` 的登录 Cookie 代理访问。

响应包含 `created`、`id`、`name`、`key`、`key_prefix`、`scopes`。这是平台登录会话内的接口，不是目前已经开放给 Skill 的授权地址。客户端不读取浏览器 Cookie、网页登录 Token，也不通过自动读取登录浏览器来提取 Key。

默认 Key 被停用、删除、不可查看或不具备去 AI 权限时，交给用户在平台处理；不自动重建、启用或扩大权限。

## 协议提供后要核对的内容

正式授权页地址、回传方式、一次授权的有效期、客户端如何核验请求关联、取消和拒绝时的行为、结果的领取和过期规则。密钥不放进 URL、聊天或日志；跨会话或错误客户端的回传不能被保存。

目前本地保存入口为 `~/.config/qiling-humanize/credentials.json`，文件权限为当前用户私有；环境变量优先。任务状态也按私有文件写入。服务端撤销或重置 Key 后，下次调用按照实际鉴权错误重新引导授权。
